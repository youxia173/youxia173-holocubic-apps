# HoloCubic 自动生活桌宠 — 产品与开发方案 V0.1

> **方案状态**：构思阶段；本文件是截至 2026-10-16 与用户讨论后形成的当前需求基线。
> **主要目标**：HoloCubic 真机。**Windows 仅作为脱离真机时的本地预览与调试工具**。
> **已有仓库**：https://github.com/youxia173/youxia173-holocubic-apps
> **重要**：以下“已经确定”的约束高于早期对话里“Windows 高清客户端、服务器优先”等已撤销构想。

## 0. 已确定的原则（必须遵守）

1. **主平台 HoloCubic**：正式 App 以其运行环境及资源约束为准；先研究现有仓库、实际 Lua/LVGL API 及资源加载方式，禁止凭空假设硬件能力。
2. **单一画面标准：320×240**。Windows 预览内容和窗口的目标客户区均为 320×240。Windows 不是独立高清桌宠，不允许第二套高清动画、独立 UI 布局或另外的分辨率方案。若 Windows 窗口边框或 DPI 影响客户区，应保证显示客户区仍精确为 320×240。
3. **一套视觉资源**：相同 Q 版角色形象、GIF、服饰/场景素材、尺寸和布局规则用于 Windows 模拟与 HoloCubic 真机。允许不同平台存在薄适配层，但不得造成两套美术资产。
4. **重要信息在底部**：设备摆在低桌面时，屏幕顶部可能被观察角度遮挡。时间必须**任何行为中始终显示**，放在底部明显的位置；主要行为/重要状态也在底部。顶部可用于次要、被遮挡也不影响使用的信息。顶部安全区建议从 24–32px 起步，但需实际调试后确定，可选配置。
5. **自动生活**：玩家不需要主动点按钮来控制当前行为；宠物根据时间、偏好和内部状态自主吃饭、学习、打游戏、睡觉，以及待机等。开发者调试模式允许强制切换动作，用于验证，不是正式玩法。
6. **网页设置**：用户希望有网页端配置界面，用于修改日程、成长偏好和外观相关设置。当前阶段应是**本地可用的设置界面**，不依赖公网服务器；具体本地实现须根据仓库架构确定。
7. **多成长路线并行**：武侠/武功、魔法、修仙、武魂/魂环可同时发展，分别储存进度。主修路线可决定默认服装和核心特效，副修进度保留。日后能够添加打工、种田、职业及其他修炼路线。
8. **成长影响外观**：例如魔法成长可解锁并穿上魔法师服装，修仙可使用仙侠服装；魂环以颜色、顺序、数量等数据驱动展示，避免为所有组合单独制作 GIF。
9. **现在不做服务器**：不用实现云端运行、WebSocket 同步、多设备共享进度、NAS、云部署、跨公网远程访问等。保持未来可扩展的边界即可。
10. **先构思并分阶段实现**：在确认架构可行性和关键性能测试之前，不应直接铺开大型复杂玩法。

## 1. 产品定义

一名可爱、统一设定的 Q 版女娃娃，初始设定参考蓝白、温柔、简洁科技感的 AI 助手气质（保持原创性）。她生活在 HoloCubic 屏幕里，根据自动日程和成长属性做事：吃饭、学习、玩游戏、睡觉，并持续显示当前时间。不同的修炼发展路线可以解锁对应服装、姿态、动画、道具与特效。Windows 在没带 HoloCubic 时承担同尺寸预览及调试任务。

角色暂用概念名 **诺诺 / Nono**，最终名称未锁定。

## 2. 显示/UI 约束

- **固定逻辑坐标系**：x=0..319, y=0..239。
- 初始布局建议（**可调整草案，不是锁定像素**）：顶部次要区 y=0..31；角色/场景区 y=32..183；底部重要信息区 y=184..239。
- 底部始终显示当前时间，推荐 HH:MM 大字；当前动作状态与重要成长进度可随行为变化，但不可遮挡时间。
- 禁止在顶部安全区放当前时间、唯一的错误提示等必需内容。
- GIF 或角色主体不能覆盖底部时间；遮挡安全区通过 Windows 预览器可视化模拟。
- Windows 预览必须和 HoloCubic 使用**相同的画面尺寸、素材、界面布局**；另设开发调试工具面板，不侵占 320×240 正式画面。
- Windows 预览只是视觉和逻辑预览，不承诺复刻设备 GIF 解码性能及字体渲染；这些仍需真机验证。

## 3. 核心行为系统（首版）

| 活动 ID | 行为 | 表现资源示例 | 备注 |
|---|---|---|---|
| idle | 待机/发呆 | idle.gif | 空闲行为 |
| eat | 吃饭 | eat.gif | 可与饥饿值相关 |
| study | 学习/修炼 | study_*.gif | 根据成长路线选择动作或素材 |
| game | 打游戏 | game.gif | 娱乐行为 |
| sleep | 睡觉 | sleep.gif | 睡眠时间段优先 |

- 各活动先有一个主要 GIF，以后允许动作变体、进入/退出过渡、情绪表现。
- 用户设置的作息和行为倾向影响自动决策，但不需要逐条操控。
- 建议采用时间日程、基础需求（精力、饥饿、心情）、行为权重、必要的状态转移限制共同决策。
- 内部逻辑应可被调试器手动指定模拟时间、倍率、固定随机种子、强制触发动作，用于可复现测试。
- 时钟由程序绘制，不预先写进 GIF；换动作时不能闪烁或消失。

## 4. 成长路线的扩展框架

设计原则：**行为（做什么）与成长（得到什么）与外观（穿什么/展示什么）分离。**

### 首批预留路线
- `magic` 魔法：独立等级/经验/法术；可解锁魔法袍和魔法特效。
- `cultivation` 修仙：独立修为和境界；可解锁道袍、灵气特效、法器。
- `martial` 武侠：独立武功经验/技能；可解锁武侠服饰、武器与动作。
- `martial_soul` 武魂/魂环：独立魂力进度，魂环列表保存颜色、顺序、属性。可显示黄、紫、黑、红等颜色组合。

### 未来路线（不要求首版实现）
- 打工/职业、工资、金币。
- 种田/农作物/时间结算/收获与背包。
- 更多修炼、炼丹、冒险等，通过注册机制接入。

### 数据模型（概念性，不规定编程语言）

```json
{
  "schema_version": 1,
  "pet": { "id": "pet_001", "name": "Nono" },
  "activity": { "id": "study", "track": "magic", "started_at": 0 },
  "growth": {
    "primary_track": "magic",
    "tracks": {
      "magic": { "level": 1, "xp": 0 },
      "cultivation": { "realm": "炼气" },
      "martial": { "level": 1, "xp": 0 },
      "martial_soul": { "power": 1, "rings": ["yellow", "purple"] }
    }
  },
  "appearance": { "outfit": "starter", "effects": [] }
}
```

此模型仅表达边界；需考虑存档版本、持久化、数据迁移、事件与扩展字段。不要一开始为多个等级/服装/魂环组合穷举大量 GIF。

## 5. 素材与动画

- 初始角色：蓝白配色 Q 版女娃娃；独特蓝色三角形发夹、浅冰蓝头发、大眼睛、可识别的头发轮廓。
- 已有四个路线的**概念设计图**：修仙、武侠、魔法、魂环；不同形象应保留同一个角色的脸、发型和辨识标识，仅服饰/道具/特效发生改变。
- 已有一个**魔法路线睡觉循环 GIF 原型**，画面 320×240，并存在透明背景版；该 GIF 是初步生成的测试素材，尚需仔细检验抠图边缘、帧间位移及硬件性能，**不能假定是最终可发布素材**。
- 优先使用相同的 GIF 文件在 Windows 模拟器和 HoloCubic 真机上渲染，实际 GIF 格式、透明、配色、FPS、解码及内存限制需要真机测试。
- 可建立 `asset_manifest`，行为根据资源 ID 寻找文件，避免在业务逻辑里硬编码 GIF 路径。
- 换装设计应注意硬件限制：可在构建/打包阶段合成动作和服装资源，特效再视性能选择分层绘制或预渲染。

### 随方案包附带的美术文件

- `assets/nono_base_concept.png`：原始角色设定图。
- `assets/nono_xianxia_concept.png`：修仙设定。
- `assets/nono_wuxia_concept.png`：武侠设定。
- `assets/nono_mage_concept.png`：魔法设定。
- `assets/nono_soulring_concept.png`：武魂/魂环设定。
- `assets/nono_mage_sleep_sprite_sheet.png`：睡眠分镜素材。
- `assets/nono_mage_sleep_preview_320x240.gif`：带背景睡眠 GIF 样例。
- `assets/nono_mage_sleep_transparent_320x240.gif`：透明睡眠 GIF 样例。

## 6. 本地 Windows 开发/预览器

- 不依赖设备在场，不依赖服务器，Windows 可独立启动调试。
- **必须显示 320×240 客户区**，与 HoloCubic 同一布局、同一套资源；不做高清独立版。
- 可另开 DevTools：切换动作，调整虚拟日期/时刻，模拟时间加速，修改经验/境界、装备、魂环配比，显示事件日志和资源加载状态。
- 需要明确：如果 HoloCubic 的 Lua/LVGL 与 Windows 使用不同运行环境，怎样防止**两份行为规则不一致**。建议尽可能共享数据定义、测试用例和确定性输入输出；评估是否可重用更多实际运行逻辑。
- 由 Codex 阅读现有仓库后提出**最小可靠的实现路线**，不先行承诺 Tauri/TypeScript/Python 等具体技术必选。

## 7. 网页配置（首期最低目标）

- 设置昵称、时间显示选项、睡眠/学习/娱乐/吃饭时间倾向。
- 设置多条成长路线的目标与主修路线（首版可少量开放）。
- 显示当前行为，查看基本成长进度。
- 保存/读取本地设置；网络方案和具体访问方式以后定。
- 网页用于**预设**，不是要求用户每隔几分钟手动命令桌宠下一步做什么。

## 8. 推荐模块边界（概念）

- `PetCore`：角色状态、时间推进与行为决策。
- `ActivityRegistry`：活动注册、调度、效果。
- `ProgressionRegistry`：路线各自的升级规则与数据。
- `AppearanceManager`：服装/特效/动画资源标识映射。
- `SaveManager`：存档、版本升级与恢复。
- `ConfigUI`：网页设置。
- `HoloCubicRuntime`：实际设备运行与绘制。
- `WindowsPreview`：仅开发预览与调试。

**重要**：模块名字仅为职责建议，开发前应先研究现有项目约定及真实设备 API。

## 9. 第一阶段建议（先做可行性实验，不是直接造完整游戏）

### 阶段 0：仓库和设备能力调查（只读）
1. 检查现有 repo 目录、编写范式、已有 app 的 Lua/LVGL/API 代码。
2. 确认加载 GIF、绘制底部时钟、文件读取、配置存储等接口在现有固件/SDK 的真实可行性。
3. 说明 Windows 同素材预览如何实现，以及哪些结果必须真机测试。
4. 形成最小目录与测试计划，**先向用户汇报**。

### 阶段 1：320×240 单画面原型
1. Windows 打开实际客户区 320×240 的预览窗口。
2. 使用已有魔法睡眠 GIF 资源显示角色。
3. 底部显示实时 HH:MM，并验证在任何动画下都持续显示。
4. 顶部以模拟遮挡层验证安全区。
5. 提供独立调试面板：强制切换睡眠/待机等动作。

### 阶段 2：自动生活与配置
1. 有限行为状态机：待机、吃饭、学习、游戏、睡觉。
2. 本地日程与权重配置；本地存档。
3. 断开真机也能调试时间流转和活动变化。

### 阶段 3：扩展性样板
1. 添加两条独立成长路线，验证同一角色并行成长。
2. 测试主修路线切换服装资源 ID。
3. 测试魂环颜色列表数据驱动展示的最小可行办法。

## 10. 当前明确不做 / 未敲定

**当前明确不做**：服务器、云部署、NAS、远程同步、多端同时展示、Windows 高清独立桌宠、另一套 UI、另一套动画资产、过早实现完整打工/种田/复杂副本。

**未敲定，需先实验或继续讨论**：最终角色名称；GIF 帧率和资源尺寸；HoloCubic GIF 透明支持及内存预算；具体行为决策公式；本地网页配置的具体运行方式；Windows 与 Lua 共享逻辑的实现路径；最终像素布局边界。

## 11. 给 Codex 的工作要求

- 阅读项目现有代码和文档后再提方案；不得臆测已存在的架构。
- **先做只读分析和分阶段开发规划；不要未经确认直接改动旧 App。**
- 不要把已经取消的服务器优先/高清 Windows 独立客户端设计重新带回来。
- 尽量把新桌宠放在独立目录，保护原有应用功能；实际路径由仓库结构决定。
- 遇到硬件 API 不确定时，用明确的假设、验证实验和回退方案说明。
- 每个阶段有明确验收标准；手动测试及真机验证项目应单独标出。
- 未得到许可，不要提交、推送远程仓库、部署或覆盖现有资源。
